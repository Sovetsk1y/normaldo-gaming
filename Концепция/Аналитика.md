# Аналитика Normaldo

Документ с предложениями по подключению аналитики и набором событий/полей. Сначала идёт минимум, который даёт честное представление о пользовательском опыте; затем продвинутый блок «когда захотим копать глубже».

---

## 1. Цели

На что должны отвечать данные:

- **Retention** — возвращаются ли игроки (D1 / D7 / D30, retention по когортам install_date).
- **Engagement** — сколько сессий, сколько раннов, продолжительность.
- **Воронка онбординга** — install → first_run → first_death → second_session → boss_reached → endless_unlocked.
- **Сложность** — на какой фазе/секунде/предмете умирают, есть ли «стена», где люди бросают игру.
- **Прогрессия** — скорость прокачки скинов, сколько до анлока следующего, активность квестов.
- **Экономика** — приход/расход пицц и долларов, инфляция метавалюты, что покупают.
- **Меню/UI** — какие экраны открывают, где зависают, не доходят до главного цикла.
- **Тех. здоровье** — крэши, FPS, время загрузки (отдельно от продуктовых метрик).

---

## 2. Предложения по решениям

Рекомендую комбинировать 2 системы — одна для продуктовых событий, одна для крэшей/перфоманса.

### Вариант A (рекомендую) — Firebase Analytics + Crashlytics
- **Плюсы:** бесплатно, уже есть Firestore в проекте → инфраструктура и креды настроены, годный отчёт по retention/funnel в консоли, есть Remote Config для A/B и удалённой настройки сложности, GA4 для глубоких SQL-запросов через BigQuery export.
- **Минусы:** GA4-интерфейс громоздкий, продуктовые воронки делать менее удобно чем в Amplitude. Лимит 500 уникальных event_name и 25 параметров на ивент — придётся следить.
- **Godot:** официального плагина нет, нужен либо community-плагин (`godot-firebase`, `godot-iOS-plugins`), либо тонкая обёртка на нативной стороне (Swift/Kotlin) с GDExtension.

### Вариант B — GameAnalytics
- **Плюсы:** бесплатно, заточено под игры, из коробки есть progression events (level/world), business events (IAP/ad), есть Godot-плагин (community). Хорошие дашборды для смерти/уровней.
- **Минусы:** меньше гибкости в кастомных событиях, экспорт сырых данных только на платных тарифах.

### Вариант C — Amplitude / Mixpanel
- **Плюсы:** лучшие воронки, ретеншн-куэри, эксплорер по событиям, free tier ≈ 10M events/мес у Amplitude (по состоянию на старт 2026 — проверить).
- **Минусы:** ещё одна интеграция, придётся катать REST поверх HTTPRequest (нативных SDK для Godot нет).

### Что предлагаю по итогу
1. **MVP:** Firebase Analytics + Crashlytics. Это закрывает 80% потребностей и не плодит зоопарк.
2. **Если в первый же месяц упрёмся в неудобство воронок:** добавляем Amplitude по HTTP API параллельно (события дублируем, не зависим от него критично).
3. **GameAnalytics** оставить на случай если захочется специализированных «game design» дашбордов без своей разработки.

## 3. Минимальный набор полей (must-have)

### 3.1 Глобальные параметры (user/session scope)

Прицепляются автоматически почти везде:
- `user_id` — анонимный uuid, генерируется на первом запуске, хранится в `SaveData`.
- `session_id` — uuid, новый при каждом старте приложения.
- `app_version` — `0.18.2+36` и т.п.
- `build_number`
- `platform` — `ios` / `android` / `editor`.
- `device_model`, `os_version` — Firebase даёт сам, иначе через `OS.get_model_name()`.
- `locale`
- `install_date` — первая дата запуска.
- `total_runs` — сколько всего раннов сыграл (счётчик из SaveData).

### 3.2 Сессии

- `session_start` — когда приложение открыли.
- `session_end` — закрыли / ушло в фон надолго.
  - `duration_sec`
  - `runs_in_session`

### 3.3 Запуск раннa

- `run_started`
  - `mode` — `campaign` (эпизод) / `endless` / `boss_test`.
  - `skin_id` — какой скин выбран.
  - `unlocked_skins_count`
  - `fat_level_start` — стартовая толщина.

### 3.4 Конец раннa

- `run_ended` (одно событие, не путать с death)
  - `mode`
  - `outcome` — `death` / `boss_defeated` / `quit_to_menu`.
  - `duration_sec`
  - `pizzas_collected`
  - `dollars_collected`
  - `phase_reached` — индекс 0–5 в обоих режимах: бесконечный идёт по той же
    таблице фаз, что и эпизод (см. [[Уровни/Бесконечный режим]]).
  - `max_fat_in_run`
  - `min_fat_in_run`
  - `skin_id`

### 3.5 Фазы

- `phase_entered`
  - `mode`
  - `phase_index`, `phase_name`
  - `time_since_run_start_sec`
  - `pizzas_so_far`

### 3.6 Смерть

- `death`
  - `mode`
  - `phase_index`
  - `cause_group` — `obstacle` / `bomb` / `molotov` / `glove` / `snake` / `dog` / `fire` / `other`.
  - `cause_specific` — `boxing_glove`, `trash_bin`, `banana_peel` … (то что в группе spawn-er).
  - `lane_y_index` — 0–4 (какая полоса).
  - `fat_level_at_death`
  - `time_in_run_sec`

### 3.7 Прогрессия / мета

- `skin_unlocked` — `skin_id`, `unlock_path` (xp/purchase/quest).
- `skin_level_up` — `skin_id`, `new_level`, `xp_total`.
- `quest_completed` — `quest_id`, `quest_type` (daily/challenge), `reward_kind`.
- `quest_claimed` — `quest_id`, `reward_amount`.
- `boss_first_defeat` — однократное событие, важный milestone.
- `boss_defeated` — поле `episode` (1–3, или 0 для бесконечного): по нему видно,
  на каком эпизоде игроки застревают.
- `endless_unlocked` — однократное.

### 3.8 Экономика (агрегированные счётчики)

Не шлём на каждой пицце — раздуем event count. Шлём аггрегаты в `run_ended` + отдельные точечные события для крупных приходов/расходов:
- `currency_grant` — `currency` (pizza/dollar/xp), `amount`, `source` (run_end/quest/iap/ad/dev).
- `currency_spend` — `currency`, `amount`, `sink` (skin_unlock/upgrade/continue/etc).

### 3.9 Меню/UI воронка

- `screen_view` — `screen_id` (`main_menu`, `skins`, `quests`, `leaderboard`, `pause`, `game_over`, `intro_throw`, и т.д.).
- `cta_pressed` — `screen_id`, `cta_id` (`start_run`, `start_endless`, `open_skins`, `claim_quest_reward`, `share_score`, `dev_*` исключить).

## 4. Продвинутая аналитика (next steps)

Добавлять по мере того, как захотим резать данные тоньше.

### 4.1 Гранулярный геймплей

- `item_collected` — батчим, шлём максимум раз в 5 сек в виде `items_batch` с массивом `{item, lane, t_sec}`; иначе разнесёт лимиты.
- `damage_taken` (отличается от death — пропустил молотов, но выжил) — `cause_*`, `fat_before`, `fat_after`.
- `near_miss` — успешно увернулся от молотова/перчатки в окне ≤ N px / N мс. Хорошо для оценки «честности» сложности.
- `inactivity_window` — игрок не двигается >2 сек посреди раннa (AFK / залип).
- `input_method` — `joystick` / `touch_swipe` / `keyboard`.
- `skill_used` — для скин-спецспособностей: `skin_id`, `skill_id`, `phase`, `outcome` (saved_life/wasted/etc).
- `density_at_event` — сколько предметов на экране в момент смерти/near-miss (тяжёлый сигнал «нечестно»).

### 4.2 Тепловые карты

- `death_heatmap_point` — позиция (`x_norm`, `y_norm` в 0..1) — после агрегации даёт картинку «где умирают».
- `pickup_heatmap_point` — то же для пицц/долларов.
- `lane_dwell_time` — сколько времени игрок провёл на каждой полосе.

### 4.3 Прогрессия и сложность

- `phase_completion_rate` — выводить через `phase_entered` + `run_ended`, отдельным событием не нужно.
- `boss_attempt` — `attempt_number`, `outcome` (defeat/death/quit), `time_in_fight_sec`, `damage_taken_in_fight`.
- `pattern_seen` — какие именно паттерны препятствий запускались (для балансировки): `pattern_id`, `phase`, `duration_sec`.

### 4.4 Меню / маркетинг

- `tutorial_step` — `step_id`, `outcome` (completed/skipped/timeout).
- `notification_received` / `notification_opened`.
- `share_attempted` — куда (system_share / clipboard / leaderboard_screenshot).
- `attribution` — UTM/идентификаторы кампаний, через AppsFlyer/Adjust (если будут).
- `ab_test_assignment` — `experiment_id`, `variant`. Прикладывается ко всем последующим событиям как user-property.

### 4.5 Монетизация (если/когда появится)

- `iap_offer_shown` — `offer_id`, `screen`.
- `iap_purchase_started` / `iap_purchase_completed` / `iap_purchase_failed` — `product_id`, `price_micros`, `currency_code`.
- `ad_offer_shown` — `placement` (continue/double_reward/etc).
- `ad_started`, `ad_completed`, `ad_dismissed` — `placement`, `network`, `reward_kind`.

### 4.6 Технические

Лучше отдельным каналом (Crashlytics + Performance Monitoring) — не пихать в продуктовую аналитику:
- crash logs (auto, Crashlytics)
- ANR / freeze
- `perf_run_avg_fps`, `perf_run_min_fps`, `perf_run_p99_frame_ms`
- `asset_load_ms` — время загрузки сцены/ассетов.
- `audio_glitch_count`

### 4.7 Социальные

- `leaderboard_view` — `tab` (global/friends/weekly).
- `leaderboard_score_submitted` — `score`, `mode`, `rank_after`.
- `skin_book_open` — какие страницы листают.

## 5. Соображения по реализации

### 5.1 Naming convention

- `snake_case` для имён событий и параметров.
- Префикс по домену: `run_`, `econ_`, `prog_`, `ui_`, `perf_`, `meta_`.
- Идентификаторы предметов/скинов/квестов — тот же id что в коде (без локализации, без эмодзи).
- Одно поле — один смысл; не переименовывать (если поменять имя — потеряем историю).

### 5.2 Версионирование схемы

- К каждому событию добавляем `schema_v` (int). При несовместимых изменениях бампим.
- Старые поля не удаляем, оставляем deprecated, добавляем новые.

### 5.3 Локальная очередь и оффлайн

- События пишем в локальную очередь (массив в `SaveData` или отдельный append-only файл в `user://`).
- Флашим:
  - при `session_end` (приоритет — самое важное);
  - при пересечении порога (например 30 событий или 4 КБ);
  - при ручном возврате интернета.
- На случай крэша — события до сброса будут утеряны, но Crashlytics поймает причину.

### 5.4 Приватность

- Опт-аут переключатель в настройках (если будет в проекте).
- Никакого PII: только uuid, никаких email/имени.
- Если будет ребёнок-режим → COPPA-флаг, и тогда отрубаем рекламные/атрибуционные ивенты.
- Документ-«что мы собираем» в about-экран при первом запуске.

### 5.5 Dev/QA фильтрация

- Все ивенты с `is_dev = true` если включён дев-режим (есть текущий дев-чип в HUD) или сборка в редакторе.
- В дашборде делаем сегмент «без dev» по дефолту.

### 5.6 Бюджет

- Firebase бесплатно до 1M событий/день, дальше — нагрузка считается. На ранчем этапе нерелевантно.
- Лимит 500 уникальных event_name — выше я уложился в ~30, есть запас.

## 7. Текущее состояние интеграции (MVP уже в репо)

Подключено через **GA4 Measurement Protocol** (HTTP, без нативных SDK).
Crashlytics отложен — нужен нативный iOS-слой; пока ничего не отлавливаем.

### 7.1 Где что лежит

- `scripts/analytics.gd` — синглтон. Зарегистрирован в `project.godot` как
  `Analytics="*res://scripts/analytics.gd"`.
- `user://analytics.cfg` — `client_id` (UUID v4) сохраняется тут, переживает
  переустановки только если бэкап iCloud включён.
- `session_id` — UUID, перевыпускается на каждый запуск приложения.

### 7.2 Что нужно вписать перед публикацией

В `scripts/analytics.gd`, секция констант:

```gdscript
const MEASUREMENT_ID : String = ""   # "G-XXXXXXXXXX"
const API_SECRET     : String = ""   # MP API secret
const USE_DEBUG_ENDPOINT : bool = false
```

Где взять:

1. **GA4 Property** — `analytics.google.com` → Admin → Create Property
   (App stream, выбрать iOS, ввести bundle id).
2. **measurement_id** — на странице созданного Data Stream (G-XXXXXXXXXX).
3. **API secret** — там же → "Measurement Protocol API secrets" → Create.

`USE_DEBUG_ENDPOINT = true` шлёт ивенты на `/debug/mp/collect` — сервер
валидирует и возвращает ошибки в ответе, но НЕ пишет в отчёты. Удобно при
первой проверке payload-ов; перед релизом обязательно вернуть `false`.

### 7.3 Что уже отправляется

**Жизненный цикл приложения**
- `app_session_start` — в `_ready()` синглтона. Префикс `app_` потому что
  `session_start` зарезервирован GA4 для auto-collection нативного SDK.
- `app_session_end` — на `NOTIFICATION_WM_CLOSE_REQUEST` /
  `APPLICATION_PAUSED`, с `duration_sec`.

**Ранн**
- `run_started` — `hud.gd` рядом с `QuestManager.notify_run_started`.
  Поля: `mode`, `skin_id`, `unlocked_skins_cnt`, `skin_level`.
- `run_ended` — `hud.gd:_on_normaldo_died`. Поля: `mode`, `outcome`
  (`death` / `boss_defeated`), `duration_sec`, `pizzas_collected`,
  `dollars_collected`, `phase_reached`, `skin_id`.
- `phase_entered` — `hud.gd:_on_phase_entered`. Поля: `mode`, `phase_index`,
  `time_in_run`.
- `boss_defeated` — `hud.gd:_on_boss_defeated`. Поля: `first_time`,
  `time_in_run`.
- `death` — `normaldo.gd:_die`. Поля: `cause_group` (molotov/fire/glove/
  snake/bomb/slowing/obstacle), `cause_specific` (имя сцены), `lane_y`,
  `fat_level`, `pizza_count`.

**Прогрессия / скины**
- `skin_unlocked` — `save_data.gd:buy_skin`. Поля: `skin_id`, `unlock_path`
  (`purchase`), `price`.
- `skin_level_up` — `save_data.gd:add_xp` (внутри цикла). Поля: `skin_id`,
  `new_level`.

**Квесты**
- `quest_completed` — `quest_manager.gd:_eval_daily` (daily) и
  `_complete_story` (story). Поля: `type` (`daily`/`story`), `tier` или
  `idx`, `cond`.
- `quest_claimed` — `claim_daily`, `claim_story`. Поля: те же + размеры
  награды.
- `entry_bonus_claimed` — `claim_entry_bonus`. Поле: `amount`.

**Экономика**
- `currency_grant` / `currency_spend` — централизованно в
  `save_data.gd:_emit_currency`, вызывается из `add_dollars`, `add_tokens`,
  `add_xp` и `buy_skin`. Поля: `currency` (`dollar`/`token`/`xp`), `amount`
  (всегда положительный), `source`.

Источники (`source`), которые уже размечены:
- `run_end` — из `_on_normaldo_died` (dollars + xp).
- `skin_level_up` — встроенные награды за уровень в `add_xp`.
- `skin_mastery` — токены за мастерство (XP свыше уровня 10).
- `skin_purchase` — `buy_skin`, всегда negative dollar (spend).
- `quest_reward` — `_apply_reward` в QuestManager.
- `entry_bonus` — `claim_entry_bonus`.
- `pending_reward` — клейм отложенной серверной награды в HUD.
- `game_over_capture` — кнопка «забрать XP» на game-over экране.
- `slot_spin` — оплата спина (`-1 token`).
- `slot_prize` — выигрыш в автомате (xp / dollar / token).
- `unknown` — фолбэк для всего, что забыли разметить (надо мониторить и
  добавлять явные источники).

**Майлстоуны**
- `endless_unlocked` — `hud.gd:_on_boss_defeated`, в момент, когда пройденный
  эпизод оказался последним. Раньше событие слал `quest_manager` при
  завершении квеста с флагом `reward_endless`, но режим открывает не квест, а
  прогресс эпизодов, и слать надо оттуда, где открытие происходит на самом
  деле. Поле: `episodes_done`.

Каждый ивент дополнительно получает `app_version`, `platform`, `session_id`
и обязательный для GA4 `engagement_time_msec`.

### 7.4 Что ещё не подключено (следующая итерация)

- `ui_screen_view` / `ui_cta_pressed` — нужно разнести по экранам меню
  (магазин, скины, лидерборд, квесты, achievements). Префиксы `ui_*`
  обязательны: голые `screen_view` зарезервированы GA4.
- A/B-привязка через `set_user_property("ab_variant", …)` — когда появятся
  эксперименты.
- Гранулярный геймплей из §4 (near_miss, density_at_death и т.д.) — по
  мере появления продуктовых вопросов, на которые этих ивентов не хватает.

### 7.5 Crashlytics

Не подключён. План: нативный iOS-плагин через CocoaPods + Swift bridge.
Альтернатива на ближайшее время — Sentry (есть community-SDK для Godot,
работает через HTTP, поэтому ставится без правки `ios_export`). Решим
отдельно.

### 7.6 Приватность / комплаенс

- Никакого PII не собираем (UUID + индексы фазы/полосы).
- При первой публикации в App Store — обновить privacy nutrition label:
  "Identifiers / User ID" (наш `client_id`), "Usage Data / Product
  Interaction" (события сессии и раннa). PII = No.
- Опт-аут переключатель пока не сделан; добавим, если решим что нужен
  (для рекламы он точно станет обязательным).
